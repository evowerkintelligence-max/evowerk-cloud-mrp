# Terraform

Two self-contained root modules for a customer-hosted deployment, one per
cloud. Each is deployed into the customer's own account/subscription;
Evowerk never hosts the state or the data.

| Module | Runs on | Details |
|---|---|---|
| [`aws/`](aws/README.md) | ECS Fargate + ALB + RDS Postgres + EFS + Secrets Manager | `aws/README.md` |
| [`azure/`](azure/README.md) | Container Apps + Postgres Flexible Server + Key Vault + Azure Files | `azure/README.md` |

## State

Both modules default to local state so a fresh clone can `terraform apply`
with no setup. **A real deployment must use encrypted remote state** (the
state holds the generated DB password and JWT secret):

- **AWS**: [`aws/backend.tf.example`](aws/backend.tf.example) - S3 backend
  with `encrypt = true` under a customer-managed KMS key, versioned bucket
  with public access blocked, and a DynamoDB table for state locking.
- **Azure**: [`azure/backend.tf.example`](azure/backend.tf.example) -
  `azurerm` backend on a versioned Storage Account (encrypted at rest,
  TLS 1.2+, no public blob access), Entra ID auth instead of account keys,
  and blob-lease state locking.

Copy the example to `backend.tf`, fill in the placeholders (the one-time
setup commands are in the file), and run `terraform init -migrate-state`.
`*.tfstate`, `*.tfstate.backup` and `terraform.tfvars` are gitignored in both
modules.

## Secrets

No secret is committed or written to a `.tfvars` in the repo:

- The DB password is generated by `random_password`, and so is the JWT
  secret unless `jwt_secret_key` is supplied; both land in AWS Secrets Manager / Azure Key
  Vault and reach the containers as secret references, never as plain
  environment values.
- Caller-supplied secrets (`mfa_encryption_key`, OAuth client secrets on
  AWS, `gemini_api_key` on Azure) are `sensitive = true` variables, passed via a gitignored
  `terraform.tfvars` or `TF_VAR_*` environment variables.
  `terraform.tfvars.example` lists them with empty values.

## Version pinning

`versions.tf` pins Terraform (`>= 1.5.0`) and every provider to a minor
range (`~>`); `.terraform.lock.hcl` is committed in both modules so every
`init` resolves the same provider builds and checksums. Dependabot proposes
provider updates weekly.

## Checks (CI, both modules)

Every PR touching `infra/terraform/**` and every push to `master` runs, per
module ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml),
`terraform-lint` job):

1. `terraform fmt -check -recursive`
2. `terraform init -backend=false` + `terraform validate`
3. `terraform test` - plan-only tests (`tests/*.tftest.hcl`) against mocked
   providers that assert the security invariants: private, encrypted
   database; only the ALB/frontend internet-facing; HTTPS enforced; secrets
   from Secrets Manager/Key Vault; every alarm routed to a receiver; input
   validation rejects bad CIDRs, keys and names.
4. TFLint with the AWS/Azure rulesets (`.tflint.hcl`)
5. Checkov policy-as-code, failing on any finding not in the reviewed
   `.checkov.baseline`
6. Trivy config scan, failing on HIGH/CRITICAL; accepted findings carry an
   inline `# trivy:ignore:<ID> <reason>`

CI holds no cloud credentials, so it never runs a real `plan` or `apply`;
the mocked `terraform test` plans stand in for plan review. Run the same
checks locally from a module directory:

```bash
terraform fmt -check -recursive
terraform init -backend=false && terraform validate && terraform test
tflint --init && tflint
checkov -d . --framework terraform --baseline .checkov.baseline
trivy config --severity HIGH,CRITICAL .
```

## Monitoring

Each module's `monitoring.tf` alerts on the signals that mean the app is down
or about to be: 5xx responses, unhealthy/restarting containers, database CPU
and storage. AWS publishes CloudWatch alarms to a KMS-encrypted SNS topic;
Azure routes metric alerts to an Azure Monitor action group. Set
`alarm_email` to receive them by email. Container logs go to CloudWatch Logs
on AWS.
